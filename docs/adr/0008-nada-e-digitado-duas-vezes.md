# Nothing known is ever typed twice

Once Corealux OS knows something, it never asks anyone to type it again. This covers trip dates, people's names, ages, hotels, destinations, flights, luggage, diets, the Cliente's language: anything. Wherever that information is needed later (the Formulário de planejamento, the Orçamento, the Proposta, the Invoice, the operational plan, the Voucher, the Aviso do dia, a Tarefa, a Mensagem), it shows up already filled in as the default. The person confirms it or changes it, and never retypes it. Juliano set this rule on 2026-09-24, and its purpose is to minimize human error. Every time a person retypes a date, a name or a hotel, they can get it wrong: a misspelled passport name, a shifted date, the wrong hotel on a Voucher. The copies then disagree, and nobody knows which one is right. The fewer times a fact is typed, the fewer chances it has to be typed wrong. Retyping the same facts into one spreadsheet, deck and chat after another is also the work the system replaces.

## Consequences

- There is one record per real-world thing. A Viajante is one record from the lead on, and later steps extend it in place. It is never copied into a second store. Counts and summaries are derived from the records, never stored beside them.
- Where a step needs a different value for its own purpose (e.g. an Opção with other dates, an Orçamento hotel different from the one the Cliente mentioned), it starts from the known value as a default. The change belongs to that step and never silently rewrites the source.
- **If the value is in the database, the field appears filled in. Always.** This is never a judgment call made per screen or per field, and there are no exceptions. Forms ask only for what is missing. The lead checklist and the Formulário de planejamento ask only for what isn't recorded yet.
- A frozen Versão, Invoice or Voucher keeps a snapshot of what it showed (ADR-0001), which is a record of what was sent, not a second source. New work always starts from the live records.
- Imports and pasted text (Excel, a client's free-text request, Formulário answers) are matched against existing records. A conflict is shown for a person to choose. A duplicate is never created.
- **Known options are picked, not typed.** Wherever a field has known options, it shows them as a list filtered first by everything the system already knows about where the person is, and then by what they type. Editing a Dia in Busan offers only Busan hotels, never Seoul's; a Tour's Guias are only those who speak the Idioma de guiamento. Options that don't fit the context are not shown at all. The known or most likely value is already selected. The last option is always open, so an exceptional case can still be entered. If what is typed there matches a known record outside the context (a Seoul hotel on a Busan Dia), it links to that record and never creates a duplicate. An exceptional value, once entered, is known: the list offers it next time, and the Admin can rename it, merge it into an existing option or make it a regular option. Where a rule depends on the field (Canal comercial, Categoria de atendimento), an exceptional value leaves the dependent values "a informar" (ADR-0001) until a person fills them. Only values the system works out itself (the Etapa, ADR-0007) and values that control access (the Papel) are closed lists.
- Specs and tickets check this: a vertical or transversal test fails if a screen asks for something the system already knows.
